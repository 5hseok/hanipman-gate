# 코드 변경점 분석 및 이해도 검증 가이드 (Explain Diff)

사용자가 지정한 코드 변경 사항을 분석하여, 인지부채를 방지하고 완벽한 학습을 돕는 인터랙티브 HTML 설명서를 **한국어로 작성**하십시오.

이 파일은 사용자의 맥 컴퓨터 내에 단일 독립형 HTML 파일(CSS 및 JavaScript 포함)로 저장되어야 하며, 파일 이름은 항상 오늘 날짜로 시작해야 합니다. (예: `/tmp/2026-07-15-explanation.html`)

## 📋 필수 포함 섹션 (모든 내용은 한국어로 작성)

1. **배경 지식 (Background)**: 이 변경 사항과 관련된 기존 시스템 구조를 설명합니다. 초보자도 이해할 수 있는 거시적인 배경지식부터 시작하여, 이번에 변경된 코드와 직접 연관된 미시적인 맥락으로 매끄럽게 연결되도록 하십시오.
2. **핵심 직관 (Intuition)**: 세부 코드 구현 내용보다는 '왜 이렇게 바꿨는지' 본질적인 이유를 설명합니다. 간단한 샘플 데이터(Toy Data)나 HTML 컴포넌트로 구현한 시각적 다이어그램을 적극 활용하십시오. (ASCII 다이어그램은 금지합니다.) 구조가 복잡해 손으로 그린 그림이 감당되지 않으면 아래 **구조 다이어그램** 절을 따르십시오.
3. **코드 워크스루 (Code)**: 바뀐 코드를 인간이 직관적으로 이해할 수 있는 논리적 단위로 그룹화하여 설명합니다. 코드 블록은 반드시 `<pre>` 태그를 사용하거나 CSS에 `white-space: pre-wrap`을 적용하여 줄바꿈이 깨지지 않게 하십시오.
4. **인터랙티브 Playground**: 사용자가 값을 직접 바꾸고 결과를 관측하며 이해하는 조작 가능한 모델. 아래 상세 규격을 따르십시오.
5. **이해도 검증 퀴즈 (Quiz)**: 이 변경 사항의 실질적인 동작 원리를 알아야만 풀 수 있는 중간 난이도의 객관식 문제를 **반드시 5개** 출제하십시오. 사용자가 선지를 클릭하면 정답 여부와 상세한 한국어 해설이 화면에 표시되는 인터랙티브 JS 로직을 포함하십시오.

퀴즈는 반드시 **Playground 뒤에** 옵니다. Playground가 모델을 만들고, 퀴즈가 그 모델을 인출합니다.

## 🎮 인터랙티브 Playground 규격

### 왜 퀴즈만으로는 부족한가 (이 섹션의 존재 이유)

퀴즈는 **인출 연습(retrieval practice)** 입니다. 선언적 사실에는 강하지만 코드 검토가 실제로 요구하는 **절차적·반사실적 이해**로는 잘 전이되지 않습니다(MOOC 함수형 프로그래밍 n=2,166에서 인출 단서는 시험 성적·최종 학점 어느 쪽도 개선하지 못함). 더 위험한 것은 **유창성 착각(fluency illusion)** 입니다 — 객관식을 맞히면 확신만 오르고, 잘 붙은 설명은 정확성과 무관하게 수용률을 올립니다(Bansal et al. CHI 2021). 이해 없이 확신만 오른 상태는 산출물이 아예 없는 상태보다 나쁩니다.

cognitive debt를 명명한 Margaret-Anne Storey의 진단 질문은 셋입니다: ① 이게 뭘 하는가 ② 왜 이렇게 만들었는가 ③ **이 줄을 바꾸면 무엇이 깨지는가**. ③은 객관식으로 *물을* 수는 있어도 *풀게* 할 수는 없습니다. 반사실은 조작해 봐야 답이 나옵니다. **Playground는 퀴즈를 대체하지 않고, 퀴즈가 인출할 모델을 먼저 만듭니다.**

### 최소 조건 (셋 다 만족하지 못하면 Playground가 아니므로 넣지 마십시오)

1. **조작 가능** — 사용자가 값·스위치·단계를 직접 바꾼다.
2. **관측 가능** — 조작 결과가 즉시 눈에 보이게 달라진다.
3. **결론 변경 가능** — 어떤 조작에서는 **사용자가 내릴 판단이 실제로 뒤집혀야** 한다. 조작해도 결론이 늘 같다면 그것은 장식이므로 삭제하십시오.

### 충실도 배지 (Fidelity — 상단에 필수)

AI가 만든 인터랙티브 설명물의 대표 실패 모드는 "코드도 멀쩡하고 보기에도 멀쩡한데 상호작용 논리가 틀린 것"입니다(EE-Eval, arXiv:2606.31012). 근사 모델을 실제처럼 보이게 하는 것은 이 스킬이 만들 수 있는 **최악의 산출물**입니다 — 틀린 확신을 제조하기 때문입니다. 배지 없는 Playground는 만들지 마십시오.

| 등급 | 정의 | 배지 표기 |
|---|---|---|
| **F1** | 변경된 함수·분기 조건을 JS로 **그대로 이식**해 브라우저에서 실행. 순수 로직·계산·조건 분기에만 가능 | 🟢 **실제 로직 이식** — 원본 `path:line` |
| **F2** | 실제 코드를 여러 입력으로 **실행해 입력→출력 쌍을 기록**하고 Playground가 그 표를 조회 | 🟢 **실측 트레이스** (n=k, 실행일 YYYY-MM-DD) |
| **F3** | IO·DB·외부 API 의존으로 실행 불가 → 동작을 **손으로 근사**한 모델 | 🟡 **근사 모델** — 근사한 부분: {무엇을} |
| **F4** | 로직이 아니라 **호출 그래프·상태 전이**를 조작(노드를 끄면 영향 범위가 하이라이트) | 🔵 **구조 모델** — 실행 동작 아님 |

F1/F2를 우선하고, F3으로 내려갈 때는 근사한 부분과 **왜 실제로 못 돌리는지**를 한 줄로 밝히십시오.

### Playground 유형 (대상에 맞는 것을 1~2개만 고르십시오. 전부 넣지 마십시오)

| 유형 | 하는 일 | 언제 |
|---|---|---|
| **① 입력 다이얼** | 핵심 입력을 슬라이더·토글로 두고 출력이 실시간 갱신 | 계산 로직, 임계값, 정렬·필터, 요금·포인트 산정 |
| **② 분기 스위치** | 조건을 켜고 끄면 실행 경로가 하이라이트되고 도달 지점이 바뀜 | 가드절, 권한 체크, 에러 핸들링, 피처 플래그 |
| **③ 데이터 여정 스테퍼** | 변수 **하나**가 태어나 변형되어 응답에 실릴 때까지 단계별 현재 값을 표시 | 요청 흐름 이해, 낯선 엔드포인트, 함수가 아니라 데이터를 따라가야 할 때 |
| **④ 실패 경로 실험실** | 정상 경로가 아니라 **딱 하나의 실패 경로**를 재현 — null, 타임아웃, 동시 요청, 권한 없음, 중복 키 | tier A(돈·권한·개인정보·마이그레이션·트랜잭션·고팬인)에서는 **필수** |
| **⑤ 반사실 스위치** | diff의 특정 hunk를 **끄면** 무엇이 깨지는지 보여줌 | 거의 모든 diff. Storey 진단 질문 ③의 직접 구현체 |

정상 경로는 코드가 **무엇을 하는지** 보여주고, 실패 경로는 코드가 **무엇을 틀리는지** 보여줍니다. ④를 넣을 수 있으면 대개 ④의 정보량이 가장 큽니다.

### 필수 상호작용 프로토콜: 예측 → 관측 → 해설

각 Playground의 **첫 상호작용 1회는 반드시 예측 게이트**를 통과해야 하며, 자유 조작(샌드박스)은 그 뒤에 열립니다.

1. 조작 UI는 보여주되 **결과 영역은 가립니다.**
2. 한 문장으로 묻습니다 — "이 값을 X로 바꾸면 결과가 어떻게 될까요?"
3. **제출 전에는 답을 어떤 형태로도 노출하지 않습니다.** 힌트·예시 답·기울임 단서·"참고로…" 문장을 붙이지 말고 질문 뒤에서 멈추십시오.
4. 제출 후 **예측과 실제를 나란히** 표시하고, 어긋났으면 어디서 갈렸는지 해설합니다.
5. 그 다음부터 자유 조작을 개방합니다.

예측이 **틀리는 순간**이 이 섹션의 전부입니다. 맞히면 확인이고, 틀리면 그 지점이 인지부채가 있던 정확한 위치입니다. 따라서 **예측이 갈릴 만한 지점**을 고르십시오 — 누가 봐도 뻔한 값을 묻지 마십시오.

### 금지 사항

| 금지 | 이유 |
|---|---|
| **장식용 인터랙티브** — 조작해도 결론이 안 바뀌는 위젯 | AI 생성 explorable의 대표 실패 모드. 어떤 조작에서도 "그래서?"만 나오면 삭제 |
| **충실도 위장** — 근사 모델을 실제처럼 보이기 | 틀린 확신 제조 |
| **전면 인터랙티브화** | 인터랙티브가 **최선일 때만** 인터랙티브. 텍스트·다이어그램이 나은 곳에 위젯을 넣지 않음 |
| **노브 과다** — 조작 대상 6개 이상 | 작업기억 4±1(Cowan 2001). 초과분은 프리셋 버튼으로 접기 |
| **친숙한 코드에 풀코스** | 숙련자 역전 효과(Kalyuga 2003). 사용자가 설계했고 자주 건드린 영역이면 Playground를 생략하고 **패턴 이탈점만** delta로 제시 |
| **외부 의존** — CDN·웹폰트·원격 이미지·fetch | 단일 파일 안에서 완결. 네트워크 요청 0 |
| **검증 안 된 다이어그램** — 확인 못 한 호출 경로를 그려서 실음 | 검증되지 않은 그림이 검증된 것처럼 읽힘 |

### 자가 검증 (생성 직후 반드시 통과)

- [ ] 조작하면 **사용자의 판단이 뒤집히는** 경로가 최소 하나 있는가?
- [ ] 충실도 배지가 상단에 있는가? F3이면 근사한 부분을 명시했는가?
- [ ] 예측 게이트가 1회 있고, 제출 전 정답이 화면·소스 어디서도 안 읽히는가?
- [ ] 조작 대상이 5개 이하인가?
- [ ] **"이 변경을 되돌리면 무엇이 깨지는가"** 에 Playground만으로 답할 수 있는가?
- [ ] 외부 네트워크 요청이 0인가?
- [ ] 다이어그램을 넣었다면 이미지는 `data:` URI로 인라인했는가?

## 🧭 구조 다이어그램

이 변경을 이해하는 데 **구조 자체가 설명의 본체**일 때 — 호출 체인이 여러 서비스를 건너뛰거나,
상태 전이가 새로 생겼거나, 파이프라인 경로가 바뀌었을 때 — 다이어그램을 넣으십시오.

**추측으로 그리지 마십시오.** diff와 실제 호출 체인에서 확인한 것만 그립니다.
확인 못 한 경로는 그리지 말고 글로 "미확인"이라고 쓰십시오.

diff 설명에서 자주 맞는 타입:

| 변경의 성격 | type |
|---|---|
| 요청이 지나는 서비스·함수 체인이 바뀜 | `sequence` |
| 상태/스테이터스 전이가 추가·변경됨 | `lifecycle` |
| 배포·승인·CI 절차가 바뀜 | `workflow` |
| 컴포넌트 경계·의존이 바뀜 | `architecture` |
| 데이터 적재·변환 경로가 바뀜 | `dataflow` |

### diff 전용 규칙

- **변경 전/후 두 장을 만들지 마십시오.** 한 장에 그리고, 이번 변경으로 생긴 노드·엣지를
  `variant: "emphasis"`로 구분한 뒤 캡션에서 "강조된 부분이 이번 변경"이라고 밝힙니다.
  두 장 비교는 독자가 눈으로 diff를 다시 뜨게 만들어 인지부채를 오히려 늘립니다.
- `architecture` 타입이면 `--repo-root <레포 경로>`로 실제 코드 근거를 붙일 수 있습니다.
  붙였을 때만 🟢 **코드 근거** 배지를 쓰고, 커밋 해시를 함께 적습니다.
- 다이어그램은 **핵심 직관(2번 섹션)** 또는 **코드 워크스루(3번 섹션)** 안에 놓습니다.
  Playground를 대체하지 않습니다 — 구조를 보여줄 뿐 조작 가능한 모델이 아닙니다.

## ⚠️ 퀴즈 출제 시 주의사항 (Critical Constraints)
- **정답 길이 균일화**: 정답 선택지만 유독 길어지는 현상을 방지하기 위해, 모든 선택지(A~D)의 텍스트 길이를 엄격하게 균일한 수준으로 맞추십시오.
- **정답 위치 무작위화**: 정답이 특정 번호에 편향되지 않도록 A, B, C, D 위치에 고르게 무작위로 분산시키십시오.
- 사용자가 버튼을 누르기 전까지 소스코드 분석을 통해 정답을 미리 유추할 수 없도록 스크립트 구조를 안전하게 설계하십시오.

## 🔗 대상 해석 (Target Resolution)

인자로 받은 대상에 따라 변경 내용을 아래 방식으로 수집한 뒤 분석하십시오.

| 인자 형태 | 수집 방법 |
|---|---|
| 생략 | 현재 작업 트리 변경 — `git diff HEAD` (없으면 `git diff --staged`, 그래도 없으면 현재 브랜치 vs base) |
| 브랜치명 | `git diff <base>...<branch>` — base는 프로젝트 git 규칙 또는 nearest merge-base로 해석 |
| PR 번호 (`#123` / `123`) | `gh pr diff <번호>` (제목·본문은 `gh pr view <번호>`) |
| `diff` 리터럴 / 파일 경로 | 현재 변경 또는 지정 diff 파일 |

diff가 크면 논리적 단위(슬라이스/파일 그룹)로 나눠 섹션을 구성하되, 4개 필수 섹션 구조는 유지하십시오.

## 🤝 impl-pipeline 연동

`/impl-pipeline`의 리뷰 단계(Step 6)에서 이 스킬이 호출되면, 대상은 **해당 슬라이스의 diff**입니다.
슬라이스 ID(`S-n`)와 base 브랜치가 전달되면 `git diff <base>...HEAD -- <슬라이스 글롭>` 범위로 좁혀
분석하고, 산출 HTML 파일명은 `날짜-S{n}-explanation.html` 형태로 저장하십시오.
