# 예시

둘 다 실제 도구로 만들고 되읽어 검증한 것이다. 손으로 쓴 게 아니다.

## example-design-doc.md

원장 문서 한 벌. `ledger decide` 를 세 번 호출해 만들었다.

볼 것은 **D-1 이 사라지지 않았다는 점**이다. `--supersedes D-1` 로 교체했더니
`## 현재 설계` 에서는 빠지고 `## 결정 로그` 에는 `SUPERSEDED by D-3` 로 남았다.
히스토리와 현재가 같은 파일 안에서 갈린다.

```bash
ledger current --file 이미지-업로드-파이프라인 --ids-only
# D-2 validation | 검증은 업로드 완료 콜백에서
# D-3 storage | 원본도 CDN 뒤에 둔다      ← D-1 은 안 나온다
```

`## 작업 큐` 의 슬라이스 셋은 각각 담당 결정(`D-n`)과 대상 파일 글롭, acceptance 를 갖는다.
게이트가 이 글롭으로 "설계 밖 변경" 을 잡는다.

## example-track.md

여러 레포에 걸친 배포 순서. 스텝 다섯이 `needs` 로 엮여 있다.

**스텝에 `status` 필드가 없다.** 상태는 프로브가 재고, 못 재면 `미검증` 으로 남는다.
이 예시를 그대로 파서에 넣으면 다섯 개가 전부 `미검증` 으로 나온다 — 프로브를 아직 안 돌렸으니
맞는 값이다.

`why` 를 눈여겨볼 것. 순서를 지키는 이유는 사람만 쓸 수 있고, 그게 없으면 나중에
"이거 먼저 해도 되지 않나" 를 매번 다시 따지게 된다.

`<org>` 같은 자리는 실제 값으로 바꿔 쓴다.
